# Week 4 — Hands-on Task: Hybrid Retrieval RAG with Source Citations (LangChain + Ollama)

**Task Code:** W4-Task1
**Module:** 2 — Retrieval-Augmented Generation
**Maps to:** 4.2 Advanced Retrieval — Hybrid search (BM25 + dense), metadata filtering
**Format:** Individual hands-on task, take-home
**Submission:** Completed `.ipynb` notebook
**Stack:** LangChain + Ollama (local models) — `FAISS`, `BM25Retriever`, `EnsembleRetriever`, `PyPDFLoader`, `RecursiveCharacterTextSplitter`, as used in class

## Objective

Build a RAG pipeline across two levels of complexity: a single-strategy baseline QA system, and a hybrid-retrieval + metadata-filtered comparison across multiple queries with cited answers. Demonstrate the full pipeline: load → chunk → embed → index → retrieve → augment prompt → generate → cite sources.

## Parts to implement (2 total)

### 1. Baseline Dense RAG QA
- Load one PDF with `PyPDFLoader`, split with `RecursiveCharacterTextSplitter` (state and justify your `chunk_size`/`chunk_overlap`)
- Embed with `OllamaEmbeddings`, index in `FAISS`
- Ask one question clearly answerable from the document
- Retrieve top-k chunks and print them, then generate an answer with `ChatOllama` — the final answer must cite the source page number(s)

### 2. Hybrid Retrieval + Metadata Filtering — Strategy Comparison
- Build a `BM25Retriever` and combine it with the FAISS retriever via `EnsembleRetriever` (define each retriever as a named variable, not inline)
- Load a second PDF so documents carry distinguishing metadata (source filename, page)
- Ask at least three questions:
  - one where hybrid retrieval clearly surfaces different/better chunks than dense-only — show both side by side
  - one where you force retrieval to a single source document via a metadata filter
  - one deliberately ambiguous/cross-document question that could plausibly pull from either PDF — show what actually gets retrieved and discuss whether it's correct
- For each: query → dense-only results vs hybrid results → chunks actually used → final cited answer

## Notebook structure requirements
- One section per part, clearly headed (e.g. `## 2. Hybrid Retrieval + Metadata Filtering`)
- A markdown cell describing what's being demonstrated in that part
- Retrievers, prompts, and chains written out as named variables — not buried inline
- Each retrieval/generation step written explicitly; a small `format_docs`-style helper is fine, but no single wrapper that hides the whole pipeline

## Constraints
- LangChain + Ollama only, matching the class notebooks — no switching to a hosted API
- Every retriever's output must be printed at least once per part (no silent chains)
- Use both class PDFs (or an equivalent two-document set) so metadata filtering has something real to filter on
- Submission is the notebook fully executed with outputs visible (not cleared cells)
